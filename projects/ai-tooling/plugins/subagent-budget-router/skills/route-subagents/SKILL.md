# 子代理模型与验收路由

本技能明确要求：适用的长任务中，主动将值得隔离的调查、实现、验证交给原生 subagent。每次创建/续派都先路由模型、思考等级，并以固定验收要求判断是否继续。用户禁止委派时不委派。主代理保留业务约束、接口决策和集成责任。

插件提供准入与账本，不会自行启动、监控或强制停止模型。**一轮是一次委派执行加主代理验收，不是模型内部消息数或工具调用数。** 不保证安装后拦截所有 spawn；内部循环须由主代理通过宿主工具中断。

## 配置入口

首选 **插件管理 → 子代理模型与成本路由 → 设置**。用户可直接配置并发数、最多执行轮次、连续无进展轮次、升级次数、模型及思考等级，无需发消息。`read_settings/save_settings` 与 `get_policy/update_policy` 共用用户账本。仅在用户明确要求代为修改时调用 update_policy；不要为绕过限制自行提高设置。

预估 token、token 软额度已移除。实际 token 用量只用于事后观察，取不到就留为未知，不推算、不参与是否续派的判断。升级保留用户模型、思考等级、并发与旧执行记录。

## 如何选择档位（每次首次委派前使用）

**模型档位与 reasoning_effort 是两个维度。** light / standard / deep / expert 表示任务需要的能力类别；真正使用哪个模型、low/high 等思考等级，读取用户 profiles，不能按下表私自覆盖。用户把 light 配成 high 时仍用该配置，只可指出其成本取舍。以下是任务路由标准，不是模型能力测评分数。

| 档位 | 判断依据 | 典型任务 | 不应归入的情况 |
|---|---|---|---|
| light 轻量 | 操作规则已知、输入输出明确、几乎不需设计判断；complexity=low 且 risk=low | 按已确定规则批量改名/格式转换、补齐模板字段、查找符号、提取日志字段、运行既定检查并归纳结果 | 虽然重复但每项需要不同语义判断；未调查的“看起来简单” bug；会改变协议语义的批量迁移 |
| standard 标准 | 目标与验收清楚，需要有限推理或局部实现，但不涉及复杂隐含约束；其余非高复杂度/高风险的执行任务 | 按既定接口实现局部功能、已定位原因的普通修复、补充业务测试、单模块评审、整理证据明确的调研结果 | 只做机械操作时没必要升到标准；跨模块不变量尚未厘清时不能仅按局部修改处理 |
| deep 深度 | complexity=high 或 risk=high，需要多步因果推理、复杂调用链或严谨验证 | 跨模块 bug、异步/并发状态问题、隐蔽生命周期问题、复杂算法修正、数据兼容/持久化回归评审 | 任务长、文件多、日志大本身不代表高复杂度；需要提出全新系统方案时应归入 expert |
| expert 专家 | 问题没有既定实现路线，核心产物是创造候选方案、发现遗漏约束、权衡系统级取舍；kind=brainstorm/design/architecture | 给新能力提出并比较多种路线、模块边界与协议设计、系统架构候选方案、在冲突约束下寻找替代设计 | 仅给几个变量起名或按模板写文案不算此类发散；按已批准设计写代码应重新分配到合适执行档 |

按以下顺序判断，不用“很难/高级/大项目”等词代替分析：

1. **看产物**：要的是新方案与权衡，还是按确定路线执行？实质方案发散/系统设计分别用 kind=brainstorm/design/architecture，推荐 expert。专家子代理只提出方案、论证和风险，不代替主代理确认需求或批准跨模块接口变更。
2. **看复杂度**：low = 规则完整、操作确定、无需推导新行为；medium = 边界清楚，需局部推理或实现；high = 多个相互影响的模块/状态/假设，需追踪因果或验证隐藏不变量。简单但重复的 implement/debug/review 也可为 low，不限于 lookup/summarize。纯机械转换使用 transform。
3. **看失败影响**：low = 局部可逆、易验证；medium = 影响可控但需业务回归；high = 数据损坏、协议兼容或关键共享行为可能受影响。高风险至少 deep，不能因操作简单而下调。
4. **记录依据**：route_task 必填 routing_rationale，用一句话说明已知规则、依赖/不确定性、失败影响和为何选该类别。例：“已确认替换映射，30 处同构调用且有回归检查，不改变协议，因此 complexity=low/risk=low。”不能只写“任务简单”。
5. **检查策略与能力**：quality 模式把 light 提至 standard；balanced/economy 均不降低上述能力要求，economy 额外禁止自动升级。推荐档超过 max_auto_tier 时交回说明，不静默降档、不偷偷修改设置。模型或 effort 不可用也不能默默继承主模型。

不要把整个长任务都放到最高档。例如“设计一个新模块”：expert 提出并比较设计 → 主代理选定接口与验收 → standard 实现有界功能 → light 完成机械迁移 → deep 检查关键兼容风险。阶段是不同子目标时可分别登记；同一个失败子问题不能靠拆阶段重置轮次。专家设计的验收应要求约束覆盖、可比较方案、取舍依据和可验证假设，不能仅以方案数量凑通过项。

更多边界案例见 [任务分档示例](references/task-routing.md)，只有分类不确定时读取。分类是主代理基于证据的判断，插件执行确定性映射，不宣称自动测得任务难度或模型智力。

## 分派与每轮验收

1. 小而明确的修改直接完成。对需要探索/试错或可独立验收的子问题，先 `get_policy`，再从当前原生工具/宿主读取实际允许的模型与 effort，作为 available_models。默认配置和历史记录不能证明账户权限。不可覆盖模型时不悄悄继承昂贵主模型。
2. 本次长任务固定 run_id（优先聊天 ID，否则生成 UUID）；语义子问题固定 task_id；workspace 使用实际绝对路径。恢复先查 report_usage。不能通过换 ID、换代理或调整验收条件重置轮次。
3. 在第一次分派前，从用户需求确定少量明确且可观察的 `acceptance_criteria`。实现任务需要对应业务结果或回归证据；不得只用“代码写完”“编译成功”代替业务验收。调查任务可用“定位到证据支持的原因、给出可复现步骤”等标准。不要把一个标准任意拆成大量小项来制造进展。
4. 按分档表填写 `route_task` 的 kind、complexity、risk、routing_rationale、能力列表和 acceptance_criteria。默认预览不占次数；执行前 `reserve=true` 加唯一 request_id。仅 `decision=admitted` 可以创建/续派；existing 先核对原生状态，不能再生成代理。保留 attempt ID。
5. 严格使用返回的 model、reasoning_effort；collaboration 工具支持时用 fork_turns="none"。给子代理最小任务包：目标、文件范围、基线、约束、验收项，以及“本轮只执行一个有界修复/调查方案并验证；验证未通过就返回失败项、证据和下一步建议，不在内部反复试错，不生成下级代理”。子代理报告不能单独作为通过证明。
6. 创建成功后 record_attempt(status="running", agent_id=实际ID)。模型参数只有宿主确认实际生效时才填 actual_model/actual_effort。原生工具确认结束/中断后才能记录终态，不提前释放并发。
7. 主代理检查结果和必要证据，对**每个原始验收项**提交 acceptance_results，含 criterion、verdict（passed/failed/not_checked）、evidence。全部通过才记 passed；任何失败或未验证都不能记 passed。未获得设备/环境验证应标 not_checked，不能因达到轮次上限而宣称完成。
8. 查看结果 next_step：complete 结束子任务；revise_plan 评估是否值得再做一轮；handoff 停止自动续派，向主干返回未满足项、轮次、证据与可选方案。不要把同一失败循环搬回主代理继续执行。

MCP 未加载时，可按本 SKILL.md 的实际路径定位插件根目录，使用 `python -B server.py --call <tool> --input <JSON文件>`；与 MCP 共用账本。不能为绕过计数另建账本。

## 续派和防循环

- 默认最多执行 3 轮（含首轮），连续 2 轮验收通过项数量没有超过历史最好结果就交回主代理。首轮若没有通过项，计为一次无进展。该指标刻意简单：有效调查如果暂未增加通过项，也可能触发停止，主代理据证据重新规划，不能伪报通过来解锁。
- 同一问题固定原始验收项。后续每轮需提供 retry_reason、evidence 与具体且不同的 next_action，说明针对哪个未满足项、采用什么新办法。重复相同重试计划会被拒绝；措辞改写不算新办法。
- 常规针对失败项修复用 fix_failed_criteria；缺信息用 missing_context，保持当前档位。有证据说明推理不足才用 reasoning_gap。升档跳过模型和 effort 完全相同的档位，不以名称变化冒充能力提升。升级仍消耗轮次，**不会重置无进展计数**。
- 环境故障和模型不可用不靠升档解决。默认最多自动升级 1 次，最高 deep；economy 模式不自动升级。用户明确指定档位才可 requested_tier + user_override，仍不能绕过轮次/无进展限制。
- 无须等轮次用完才停：同样失败重现、没有新证据/新方案，立即交回。主代理发现子代理在一个未结束轮次内部重复修改/测试时，使用宿主中断工具，确认终止再记 failed/blocked。插件无法硬性数清原生内部步骤，不得宣传该能力。
- 同模型/effort且确认 agent ID 时可 followup 续派，但每次都先登记新轮次。换模型新建替代代理，交接精简结论；不要继承整个实验历史。旧版没有验收项的任务不能直接自动续派，先交回主代理审查。

## 用量与说明

`report_usage` 显示轮次、逐项验收、无进展计数和 next_step。未知 token 不记为估算或零。上报 token 必须是该次执行的实际用量并附来源，不能重复填线程累计值；输入包含缓存子集，输出包含 reasoning tokens，避免重复计数。用户配置价格且用量已知时可以展示价格折算，它不是订阅实际扣费，也不控制续派。

参数、默认设置与示例见 [操作说明](references/operations.md)。
