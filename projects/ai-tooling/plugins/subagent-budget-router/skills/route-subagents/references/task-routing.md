# 任务分档边界示例

以下是均衡模式的推荐档，实际模型和思考等级取自用户 profiles。自动上限/宿主可用性不足时交回；例子不是绕过上限的授权。

| 任务 | kind / complexity / risk | 推荐 | 原因与验收方向 |
|---|---|---|---|
| 依据批准的字段映射转换 200 份 JSON | transform / low / low | light | 重复的是已知规则；验收映射覆盖、输出可解析、差异符合约定 |
| 依据模板补 30 个配置声明 | implement / low / low | light | 没有新行为设计；验收声明与模板/清单一致 |
| 提取报错时间、模块和调用栈位置 | lookup / low / low | light | 只提取事实；根因推断另建合适难度子任务 |
| 按已确认接口实现列表分页 | implement / medium / medium | standard | 有明确边界但要处理状态和业务分支；验收翻页、末页与失败恢复 |
| 修复有稳定复现且原因已确认的边界判断 | debug / medium / low | standard | 按已知因果修复并回归；若只是已确认的一处机械替换可主代理直接做 |
| 排查 NPC 退出交互后异步回调写回已回收对象 | debug / high / high | deep | 生命周期与异步状态交错；验收复现路径消失且其他退出路径保持正确 |
| 给大型文件按既定章节生成索引 | summarize / low / low | light | 输入长不等于推理复杂；材料超长可分片，不能仅因长度升档 |
| 解释多份互相矛盾的日志并找出竞态原因 | debug / high / medium | deep | 有竞争假设，需要跨事件证据验证 |
| 批量迁移公开协议字段，但旧客户端兼容规则不明 | review / high / high | deep | “批量”不意味着机械；先查明兼容边界，不能直接变更 |
| 为没有既定方案的新交互能力提出可比较实现路线 | brainstorm / high / medium | expert | 需要提出不同路径、遗漏约束与权衡；不是只列几个名字 |
| 设计多端任务同步模块边界、状态协议和失败恢复 | architecture / high / high | expert | 系统级候选方案；最后的接口/需求裁决仍归主代理 |
| 按已批准的同步协议补 DTO 和序列化代码 | implement / low / low | light | 设计已经收敛且确属同构实现；若实现中发现兼容不确定性需重新评估 |

## 常见误分

- **只看代码量**：20 行并发修复可能需要 deep，200 行模板生成可能只需 light。
- **把未知当简单**：“按钮没反应”在查明之前不能直接标 low。先委派一个有界定位任务，拿到证据后再判定修复档位。
- **把所有 bug 都交给专家**：已知目标的因果排错通常用 standard/deep；只有需要重新提出系统方案时才用 expert。
- **专家包办整个任务**：方案选定后，执行阶段重新按自身难度分档。
- **失败一次就升级**：先分清缺资料、环境问题、实现错误与推理不足。只有后者才触发 reasoning_gap；所有失败仍受验收轮次约束。
- **把档名当实际能力**：light 和 standard 若配置了相同 model/effort，实际运行配置相同。真正升级时跳过重复配置；不会自动改用户的 effort。

## routing_rationale 示例

好：“接口和字段映射已确认，任务是逐项生成同构代码，有现成回归且不改变兼容规则，因此 low/low。”

好：“退出回调、对象池和状态机都参与，复现依赖时序且可能污染复用对象，因此 high/high，选择深度排错。”

好：“尚无既定架构，需要比较事件驱动与集中调度在一致性、延迟和维护成本上的取舍，因此 architecture，推荐专家提出候选方案。”

不足：“这是简单任务”“看起来复杂”“为了效果最好用专家”。
