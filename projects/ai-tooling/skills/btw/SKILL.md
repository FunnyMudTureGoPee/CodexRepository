# BTW 插问

保护主聊天上下文是首要要求。插问的检索、代码阅读、日志、推导、方案迭代与长答案留在子代理或子聊天中。父代理只负责最少量的派发、必要状态和用户明确要求带回的结论；保持原主任务的目标、约束、决定与进度。

## 入口与调度

- `/btw 问题` 或 `$btw 问题`：默认一个子代理处理，父聊天仅收到最短结论。
- `/btw agent 问题`：明确使用子代理。
- `/btw fork 问题` 或“把这个插问开成分支”：独立分支，并通过侧边聊天显示；回答与追问留在侧边。
- 用户明确要求完全不向主聊天回传内容：使用宿主支持的独立侧聊路径，不采用会自动回传结果的子代理模拟完全隔离。

按追问连续性而非问题长度或难度调度。一次性问题使用子代理；同一话题的追问复用原代理。只有用户要求独立展开或开分支时升级为分支。升级只传递原问题、已有结论的必要摘要、证据位置和未决问题，不将完整子代理调查读回父聊天。

首个独立词 `agent` 或 `fork` 后有问题时才解析为模式参数。仅有命令但上下文无法唯一确定问题时，简短询问问题，不创建空任务。不要在每次调用时重复说明工作流。

## 上下文单向流动

1. 父聊天向旁支提供解决问题所需的背景；旁支不执行继承历史中的父任务。
2. 父代理不为插问预先检索、批量读文件或另做一遍调查。将证据路径交给旁支，让旁支自己读取。
3. 父聊天只保留已有派发回执中的话题标识与代理/聊天 ID。不要为记录映射创建业务文件、改全局记忆、改 AGENTS.md 或总结覆盖原主任务。
4. 不主动拉取旁支全文或转发中间消息。主任务的交付和总结不混入旁支讨论。
5. 旁支结论只属于插问。只有用户明确要求“采纳到主任务”或“把这点带回来”时，才将指定的最少信息纳入主任务；插问和追问本身不等于修改主任务范围。

## 子代理模式

使用宿主实际提供的原生子代理工具，仅创建一个代理。默认以 `fork_turns="none"` 和精简背景隔离上下文；只有问题确实依赖完整历史时才使用历史继承。省略模型和思考等级覆盖，沿用用户现有设置。

派发时必须包含输出约束，因为代理的最终答复会自动进入父上下文，父代理事后缩写无法消除已经回流的内容：

```text
你负责一个与主任务隔离的 BTW 插问，只读调查并解答，不继续父任务，不修改文件或应用状态，不再创建代理或分支。
问题：{原问题}
相关背景与证据路径：{最少必要信息}
检索结果、源码、日志与详细推导保留在你自己的上下文；不要向父代理发送进展消息或调查正文。
最终只返回可直接回答问题的最短结论，通常 1—3 句；必要时带一个关键来源或会改变结论的不确定点。不要附长引用、完整代码、完整日志或检索输出。
后续追问将交给你继续处理。若用户明确需要详细答案，先返回一句说明需要侧边聊天承载，不把长答案回灌父聊天。
```

父代理继续不依赖答案的主任务。没有其他工作时等待结果；收到后只展示一次最短 BTW 答案，不重复总结。无需再次读取子代理完整历史来“核对”。后续追问用 `followup_task` 等实际可用工具传给原代理，附同样的精简回传约束，不在主聊天独立展开分析。原代理不可用时，用已有最短结论和必要背景恢复到一个新代理。

不要在子代理不可用时退化为父代理执行完整插问调查。说明可改用原生侧聊入口，保持隔离要求。

## 分支与侧边显示

此模式要求的是承载对话的侧边聊天面板，不是左侧聊天列表出现一个条目，也不是只返回新聊天链接。

先检查宿主实际工具 schema 是否支持创建/打开侧边聊天，或将已有分支显示在侧边。若需要 UI 操作，遵循 computer-use skill，并以实际 UI 状态确认；不要猜测深链、私有 API、隐藏参数或把普通网页面板当作聊天面板。

当前已核实的能力边界：`fork_thread` 创建继承历史的聊天，但没有侧边显示参数；`open_in_codex` 的 right placement 不支持打开聊天，不能用它包装聊天深链实现侧聊。原生 `/side` 可启动临时侧聊，但不据此声称它能承载指定的持久 fork。后续宿主提供新接口时以当次 schema 为准。

如果没有已验证的侧边显示路径，不先创建普通 fork 再称为完成：只告知用户可使用 `/side` 打开临时侧聊，并简短说明指定 fork 的侧边展示尚不可用。只有用户接受普通分支作为替代，或侧边显示路径已确认可用时，才创建普通 fork。

创建分支时，发现并读取 `fork_thread`、`send_message_to_thread` 等实际 schema。默认同目录，不创建 Git 分支或 worktree。使用真实子聊天 ID 派发问题：

```text
这是独立的 BTW 插问分支。继承的父聊天历史仅供查阅背景，不继续其中的主任务，不再次分叉。
本次问题：{原问题和当前追问}
必要的已有结论或证据位置：{最少信息}
请在这个子聊天中完整回答并承接后续追问。不向父聊天发送消息、进展、摘要或结果。默认只读调查，不修改父任务共享文件或应用状态。
```

保持模型和思考等级不变。派发回执足以确认消息是否被接收；不要例行调用 `wait_threads` 或 `read_thread`，因为即使即时快照也可能把答案或进展正文带回父上下文。用户明确要求查状态或取回某结论时，只返回必要字段或指定片段，不输出原始结果。

有侧边展示能力时实际打开并确认子聊天显示在侧边，再在主聊天给一条简短回执；答案始终留在侧边。创建成功但派发或展示失败时，保留并复用同一 ID，准确报告未完成的步骤，不重复创建或声称已显示。

## 真实隔离边界

Skill 本身不能从父聊天删除已提交的用户消息、工具调用、系统自动回传或已出现的文本，也不能保证零 token 回流。子代理模式提供最小回流与业务语义隔离，不是严格的零上下文写入。真正不进入主聊天的插问应从宿主原生侧聊入口发起。仅在相关时把这一限制简短放在答复末段，不每次重复免责声明。
