# 在计划模式中讨论功能与模块设计

围绕用户的需求文档或任务描述，在 Codex 内置计划模式中共同完善技术方案。覆盖新增功能、新建模块、现有模块改造及混合任务。以聊天中的方案和内置计划展示承载讨论，在计划中加入足够具体的业务代码，使用户能理解设计选择及其运行效果。

## 衔接内置计划模式

遵循当前会话实际生效的模式和工具权限。已处于 Plan 模式时，使用宿主提供的提问与计划展示机制，并遵循该模式规定的最终计划格式。若要求使用 `<proposed_plan>`，将收敛后的完整方案及关键代码放入该块。

Skill 指令本身无法切换宿主模式。当前处于 Default 模式且缺少模式切换工具时，简短提示用户通过 `/plan` 启用计划模式，同时继续可完成的源码调查与方案讨论。以宿主实际模式状态判断切换是否生效。

默认将设计保留在对话及内置计划中。用户明确要求保存或导出时，再按其指定路径、格式及当前模式允许的操作落盘。计划讨论期间以只读调查、问题澄清和设计代码展示推进工作。实施需结合用户的实施指令与宿主模式执行权限。

## 逐轮讨论并更新方案

先读取必要资料，给出对业务目标、主要场景和接入位置的具体理解，再与用户讨论影响方案的选择。能由代码和文档确认的信息由自己调查。对产品语义、职责边界、数据来源等需要用户判断的问题，提供简洁选项、推荐理由及各选项对行为和实现的影响。

每轮聚焦当前最影响设计的少量问题。提问前展示足够的场景、流程或关键代码，让用户能够判断选择的后果。按当前模式和工具可用性使用原生提问工具，遵守工具的适用范围。实质性分歧需要用户回答后再确定依赖它的方案，期间可以继续独立的源码调查。

收到反馈后，将决定同步到相关职责、接口、数据流、代码片段及验收条件。解释这次决定如何改变方案，按需展示受影响的部分。将已确认的决定、合理假设和仍需讨论的事项保持清晰，避免反复询问已有答案。小任务可在一轮内完成讨论，复杂任务随决策逐步展开。

需求和关键设计选择明确后，在内置计划中汇总可供评审与实施的完整方案。用户继续讨论时，持续修订同一方案。最终计划应自包含，包含此前确定的关键业务代码与设计依据，便于用户直接评审，也便于后续实施接续。

## 从需求建立设计依据

读取需求中的业务目标、使用场景、输入输出、范围和验收条件。将场景落实到用户或调用方可观察的行为。对影响职责划分、公开契约或数据语义的缺失信息，先查项目资料，仍无法确定时说明假设及影响，必要时询问用户。

按作用域阅读 `AGENTS.md`、架构和模块文档、相关专项规范，以及有代表性的同类实现。识别项目既有的目录与命名、分层、依赖方向、生命周期、错误处理、数据所有权、协议及配置生成方式，使方案与项目已有风格和通用约定一致。沿用与需求匹配的机制和扩展点。

根据任务选择调查入口，可在同一方案中组合使用。

- **新增功能**　定位业务入口及其所在模块，确认现有能力可复用的部分，追踪功能需要接入的数据、服务、界面或事件链路，说明新增职责归属。
- **新建模块**　调查相邻模块、基础框架和同类模块的注册及调用方式，说明独立建模块的依据，定义职责边界、对外接口、依赖方向、数据所有者及生命周期。
- **现有模块改造**　沿真实入口追踪当前调用链、状态更新和对外契约，确认具体问题、影响范围和需要延续的行为。

用已核对的文件路径和符号支持现状判断。对拟新增的文件、类型和接口明确标注「拟新增」。若只有需求而缺少源码，将设计依据与待核实的接入点写清楚。发现文档与实现不一致时，依据仓库规则处理，说明证据和需要同步的文档。

## 形成能接入项目的方案

先说明目标行为及其在项目中的位置，再展开关键组件的职责和协作。围绕实际需求覆盖以下适用内容，随讨论逐步展开，按任务规模组织篇幅。

- 功能入口、主要场景及边界条件。
- 模块划分与复用依据，各组件承担的业务逻辑，对外接口及直接调用方。
- 数据模型、数据所有权、写入时机和状态变化，涉及持久化时说明路径及读写机制。
- 从输入到处理、状态更新、结果反馈的完整调用链。涉及异步时说明回调时序、错误反馈和资源释放，按需求处理取消、重试或并发。
- 接入步骤，包括适用的注册、初始化、事件订阅与注销、路由或界面入口、依赖注入、配置和协议生成。给出具体接入位置和调用关系。
- 对已有调用方、数据格式及运行行为的影响。发生契约变化时给出兼容或迁移安排。

新增模块也需要展示其如何被创建、注册和调用，使读者能够沿项目入口走到新逻辑。抽取公共能力需有当前需求和调用场景支撑，结合项目已有抽象确定合适的层级。

## 在计划中展示业务代码细节

从一个用户或调用方能够辨认的业务场景展开。新增功能讲清需求背景、现有能力和需要补齐的能力，再沿场景说明目标流程。模块改造结合现状中的具体问题说明设计理由。用连续段落和有信息量的标题串联，跨层或异步链路复杂时补充 Mermaid 流程图或时序图。

用技术博客式叙述将业务场景、设计理由和代码连在一起。把关键代码嵌入每轮方案及最终计划的对应讲解中。对主要组件的入口、核心算法或决策分支、状态写入和协作调用提供带语言标记的具体代码块，并解释输入、关键处理、输出及设计理由。代码的细节应足以让读者理解行为，篇幅集中在本次设计的关键部分。

围绕关键用例展示业务字段、条件判断、计算规则、状态转换、调用顺序和结果反馈。按真实需求展示权限或拥有判定、协议请求与推送处理、持久化或界面刷新等决定业务行为的部分。核心方法应给出足够完整的函数体，关键分支应写出实际拟议逻辑，辅助样板可适量省略。每段代码说明它解决哪个业务问题，以及它如何接入前后步骤。

当设计取舍影响业务规则时，展示相关代码或输入输出示例，让用户看到不同选择将如何改变行为。源码摘录和拟议代码是设计讨论的依据，验证状态需要据实注明。

- 明确标注「现有代码摘录」「拟议实现」或「伪代码」，注明文件和类型或方法，以及片段在完整链路中的位置。
- 拟议实现采用项目惯用的接口、命名、返回值、异步方式和错误处理。说明所引用的新增符号及其职责，核对已有符号的实际签名。
- 关键逻辑使用具体代码展示。尚未确定的外部协议或依赖可用伪代码表达，并说明待确认内容。省略部分需标明范围，保留决定行为的关键分支和必要上下文。
- 新增功能展示触发入口到结果的关键实现，新模块展示注册或装配与调用示例，改造场景展示理解行为变化所需的原逻辑和拟议逻辑。

## 醒目标出公共层和底层修改

涉及公共接口、框架基类、基础设施、共享数据结构、公共工具或跨模块默认行为时，先检查实际调用方和约束，确认变化影响谁。即使任务主体是新增功能，也需要检查其接入是否改变了这些已有契约。

评估业务层局部适配、现有扩展点或兼容入口能否满足需求。确需修改公共契约时，说明必要性和最小改动范围，在对应方案和代码之前放置警示。使用 GitHub 风格 Markdown 警示块，并保留加粗标题以兼容普通 Markdown 渲染器。

> [!WARNING]
> **公共层或底层改动 · 类型或方法名**
>
> **影响范围**　列出已核对的调用方，以及将变化的输入、输出、时序或数据行为。
>
> **修改依据**　说明现有扩展方式的限制、需要修改的原因与最小范围。
>
> **兼容与验证**　交代旧调用方、旧数据或版本交错的处理方式，按实际风险说明验证、迁移和回退条件。

对不同契约分别标出警示。尚未核实的调用范围或兼容策略，应在警示内注明待验证或待决策。拟新增通用基础能力时，说明当前使用方、必要性与维护责任，并对它引入的实质性共享约束使用同样的提示。

## 收敛为可评审的完整计划

在最终计划中汇总讨论确定的目标、业务流程、模块职责和关键实现代码，再补充有依赖关系的实施顺序，列明主要新增或修改文件、职责、接入工作，以及适用的配置、协议或文档更新。验收条件使用可观察的结果表达，覆盖核心场景、相关失败路径和实际受影响的已有行为。明确源码已确认的事实、设计假设以及待实施后验证的结果。

提交完整计划前，检查此前讨论的决定和最新代码片段已纳入，再沿场景从触发入口走到最终结果，核对关键代码、文件符号、职责、数据流和接入步骤是否相互吻合。确认新增模块有可到达的调用入口，方案符合项目约定，关键实现有代码说明，实质性公共层或底层契约变化有就地警示。
