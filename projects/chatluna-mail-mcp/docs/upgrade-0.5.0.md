# 升级到 0.5.0（V0.5）

本版本合并交付可靠性、上下文诊断及运行管理三个迭代阶段。没有单独发布 0.3.0/0.4.0 安装包。

## 新增能力

- 持久化重试队列：明确失败可由管理员重试；任务可以显式允许暂时性失败自动重试。
- 重试复用原邮件和模板快照，不再调用模型或改写正文；部分失败仅重试明确被拒绝、且未被接受的收件人。
- 自动退避、尝试次数上限、取消和安全重新排队；未知结果绝不进入重试。
- 每次重试重新检查全局开关、收件白名单、Agent 权限和任务授权快照；任务更改会阻止原自动邮件继续重试。
- 上下文支持“当前分支最近消息”或“自上次成功/部分成功发信后的新增消息”，可设置时效、最低新增数和预算溢出策略。
- 只读上下文诊断返回实际预设、模型、消息数量、预算、来源边界，不返回聊天正文、不调用 LLM。
- 运行历史按类型/状态筛选和分页；判断记录区分是否实际调用了模型。
- 清理预览、确认执行和默认关闭的自动保留期清理。
- 旧正文和过期草稿内容清理后不可恢复；投递和调度幂等标识保留，不会因清理而重复发信。
- 图片默认固定保留；仅取消固定、超过保留期且无引用的图片移入可恢复回收区。没有永久删除图片的接口。
- 长模型调用期间仍可点“暂停本次实例发送”；新增恢复操作。
- 单条损坏任务在管理页报告，不影响其他任务调度。

## 更新方式

先备份当前 Koishi 配置、SQLite 数据库和 data/chatluna-mail 资源目录，再升级：

```powershell
& "D:\AI\文献\koishi-plugin-chatluna-mail-mcp\scripts\install.ps1"
```

脚本默认使用 AppData 下的 default 实例，自动发现 Koishi 自带 Node。支持 -KoishiDir / -NodePath 指定其他位置。重新加载插件后页面应显示 0.5.0。
MCP URL 和 Bearer Header 沿用现有配置；重新连接后增加 get_mail_task_diagnostics，只读工具总数为 9。

## 新配置（默认值）

| 字段 | 默认值 | 作用 |
|---|---|---|
| autoRetryEnabled | false | 允许任务自动重试；还需该任务 retryOnFailure=true |
| maxRetryAttempts | 2 | 原邮件之后最多重试次数，手动和自动共用 |
| retryDelayMinutes | 5 | 自动退避基数；第 1、2 次分别等待 5、10 分钟 |
| cleanupEnabled | false | 开启每日自动内容精简；默认不开启 |
| retentionDays | 30 | 旧正文、草稿和未固定孤立图片的保留天数 |
| maxDecisionsPerHour | 60 | 所有任务共用的判断尝试次数上限，含规则跳过 |

重试每 15 秒检查一次。手动重试不要求 autoRetryEnabled，但始终需要 enabled=true 才会投递。
关闭自动重试会冻结未执行的自动队列；可以取消，或开启后继续。暂停当前实例也会停止队列。
临时故障重试只针对确定未提交的连接/DNS失败或明确 SMTP 4xx 拒绝；超时、断连等无法确认结果的情况标记 unknown。
凭据错误等确定失败可在修复后显式安排手动重试，不会自动不断尝试。

## 上下文选项

| 任务字段 | 默认值 | 说明 |
|---|---|---|
| contextMode | recent | since-last-send 只取上次发信检查点后的新增文本 |
| contextMaxAgeHours | 0 | 0 不限制；大于 0 时检查最近文本时间，没有时间信息则停止 |
| minNewMessages | 0 | 0 不限制；可要求自上次发信后至少有指定数量新文本 |
| contextOverflow | reject | trim-oldest 可显式移除最旧消息；不会裁掉预设和任务规则 |
| retryOnFailure | false | 本任务是否允许确定暂时性失败自动重试 |

检查点不在当前分支时，新增模式会停止并报告；不会把整个聊天历史冒充新增内容。
没有新增消息或不足最低消息数时直接记录 skipped，不额外调用模型。其余是否发送仍由指定的单个 ChatLuna 模型判断。
诊断会解析预设并检查模型是否可用，但不进行 LLM 生成。没有接入动态 RAG、其他插件长期记忆或图片识别。

## 清理边界

保留期按记录最后更新时间计算；取消图片固定也会更新该时间。先在“运行维护”预览计划，检查范围，再确认执行。预览有效期 10 分钟，数据变化后必须重新预览。
执行期间要求没有活跃判断或草稿创建，并与发送串行化。待重试邮件的原内容受到保护。
正文精简和草稿失效不可逆；图片回收可恢复并重新固定。
记录 ID、状态、哈希和最小授权/上下文检查点会长期保留，因此此功能不等于删除全部个人数据或保证数据库文件立即缩小。SQLite 文件压缩不在此版本范围。
未固定图片的回收只是移动到 .trash，不立即释放图片占用的磁盘空间。当前未提供永久清空回收区操作。
首次启用自动清理前应先人工预览；启用 cleanupEnabled 后，按该保留期执行清理即视为管理员配置的策略。

## 新命令

```text
mail.diagnose <taskId>
mail.retry <deliveryId>
mail.retry-cancel <retryId>
mail.cleanup-preview
mail.cleanup-apply <planId>
mail.asset-restore <assetId>
mail.resume
```

mail.cleanup-apply 是明确的执行操作，不是预览。图片固定/取消固定、记录筛选和重试队列均可在管理页操作。

## 兼容与回滚

- 数据表不变，新增 retry、cleanup-plan 和 maintenance 类型记录。
- 0.1.0/0.2.0 任务缺少新字段时采用兼容默认值；旧草稿内置 v1 布局和幂等记录仍受保护。
- 重启恢复 running 重试；若对应投递已经不确定，则保留 unknown，不再次发送。
- 新版任务字段不能直接由旧版严格 schema 解析。需要降级时，恢复升级前的配置和数据库备份。
- 开发源码快照：dist/source-0.2.0-before-0.5.0.zip；旧安装包保留。
